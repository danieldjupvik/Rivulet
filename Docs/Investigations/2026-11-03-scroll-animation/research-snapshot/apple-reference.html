1. Recovered UIKit focus scrolling

_UIFocusDisplayLinkScrollAnimator in UIKitCore drives real content offsets each callback. This is compiled system behavior, not a timing curve estimated from a video. See the full numeric finding ledger.

Route boundary: the observed caller targets (0, -collection.adjustedContentInset.top) and skips the operation if already at that offset. This is a conditional return to the collection's top in hero/metadata focus processing. It is not proof that all downward moves, every shelf transition, or the canonical detail page use this spring. Caller flag names and runtime template selection must not be guessed from neighboring metadata.

Read the complete spring body, selector identities, and the original caller. The damping number alone does not establish the rendered damping regime: QuartzCore's default options and spring evaluator matter.

3. Follow-up: ordinary rows on browse and detail pages

The compiled ordinary vertical-stack path uses UIKit's shared focus-scroll machinery. This conclusion now rests on positive app-side construction/configuration and a system-side call chain, rather than only inheritance or the absence of an obvious custom animator.

The system-side path is:

UIFocusSystem finishes a focus update
  → _UIFocusSystemSceneComponent receives didFinishUpdatingFocus
  → its _UIFocusScrollManager performs necessary scrolling
  → _UIFocusDisplayLinkScrollAnimator retargets/drives the offset

Original anchors: UIFocusSystem._updateFocusWithContext:report: 0x193b16b64 → did-finish method 0x193b18a2c → scene delegate 0x193bbe2c4 → scroll manager via 0x193bbe324–334. Scene setup at 0x193bba768 creates the manager, whose initializer creates the display-link animator. The manager's request path 0x193b3c09c calls the animator's target-setting method at 0x193b3c478, through resolved selector stub 0x1980f7b50. Collection-view callbacks do not directly call the manager; the scene does so after the focus notification phase. See the system-chain ledger for bodies, gates and stubs.

Movie/show detail implication: Canonical detail templates share this ordinary stack path with MediaShowcasing browse stacks. Normal row-to-row focus movement therefore has the same system animation owner and non-paged exponential model. Their layouts and target-offset policies can choose different landing positions and distances; the shared model has no universal fixed duration. Different apparent movement does not by itself establish a different animator.

UIKit's scroller gate at 0x19463acbc requires scrollable content and isScrollEnabled, and excludes active focus fast-scrolling except when ending that mode. Target resolution is separate: continuous, paging, differential and centered resolvers exist. Paging can select the distinct 0.979 convergence. Thus the result covers ordinary focus transitions, not every gesture, held-button fast-scroll state, paged carousel or manually animated offset change.

The directly inspected common initialization hooks contain no paging/convergence override or custom offset-driver setup. This is a bounded check, not proof that arbitrary later configuration cannot alter the view. The exact live controller/template on an individual server-delivered movie/show screen remains unobserved. Likewise, the previously found MediaShowcasing top-return spring must not be generalized to Canonical hero-to-first-row transitions. Touch momentum, Reduce Motion variants and custom hero interruption remain separate questions.

Additional row-adjacent effects are not the offset animator: StackTemplate focus code 0x23a043f30 forwards to its superclass and updates focus restoration/index-path state. StackViewController helper 0x23a182e30 registers coordinated unfocusing work; its closure updates adjacent-section visibility, including a branch logging hideSectionAboveIfNeeded. Such surrounding effects can change the visual impression while UIKit still owns the scrolling.

Implication for Rivulet

There is now a concrete reason to avoid one universal “Apple scroll curve.” Ordinary row scrolling and the return-to-hero transition have different evidence. For a subsequent implementation, first decide which route to match: the recovered focus model supplies an evidence-based reference for velocity continuity and precision; the app-specific spring supplies a separate reference for the demonstrated top-return route. Implement with public UIKit/Core Animation APIs and an independently written driver. Preserve Rivulet's row placement and input ownership. These findings do not justify importing private APIs or changing hitch-related rendering work.
